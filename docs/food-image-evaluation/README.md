# 食物照片辨識與營養配對測試

測試日期：2026-11-13。測試樣本為專案 `food_picture` 的全部 13 張 JPEG。

## 結論與範圍

問題同時來自模型命名、食品配對、烹調狀態及前端呈現，單純增加資料庫不能保證辨識更準。
修正後能避免這批照片中已確認的雞腿→雞腿菇、高麗菜→水餃、水餃→水餃皮、糯米腸→豬大腸等錯誤。
滷肉飯保留白飯、滷肉、滷蛋、小黃瓜；便當配菜會分開列出，未能確認菜種的項目仍保留待確認。

這是針對現有樣本的錯誤修正與回歸測試，不是獨立驗證集上的辨識準確率評估。
沒有餐點秤重、完整配方、包裝標示或實驗室數值，無法宣稱營養估計達到某個準確率。
模型仍可能漏看遮住的食物、猜錯品種或口味；官方一般食物資料也不等於實際店家的配方。

## 官方資料與使用順序

1. **TFDA 優先**：先找同一食品、官方俗名或經核對的同義詞，並檢查生熟、乾濕、濃縮與單位相容性。
2. **USDA 備援**：沒有合適的 TFDA 食品與食用狀態時，才使用相符的 USDA FNDDS 一般食物參考值。
3. **兩邊都不足時保留缺漏**：不讓 AI 產生營養數字，不把整道菜換成其中一項原料，也不為了有數字而硬配其他食品。

使用者自己建立的食品另保留既有搜尋入口；若用於照片自動配對，仍需符合食品身分與份量單位。
TFDA 原態蔬菜可作食材參考，但不包含另外加入的油、醬汁與生熟重量變化，結果會顯示提醒。
一般熟水餃可作未知內餡的參考值，明確要求確認內餡及總重量。
USDA 燉肉、雞腿及含湯泡麵均標為參考資料，不宣稱是台式滷汁、特定品牌或店家餐點的實測值。

| 資料 | 本次匯入 | 官方來源 |
| --- | ---: | --- |
| TFDA 食品營養成分資料集 | 230,152 列分析項，2,213 筆食品，保留官方俗名與描述 | [政府資料開放平臺](https://data.gov.tw/dataset/8543)、[官方 JSON ZIP](https://data.fda.gov.tw/data/opendata/export/20/json) |

USDA FNDDS 為官方彙編的飲食調查食品資料，並非台灣餐點實驗室檢測。少量中文名稱與配方對應由本專案人工整理；數值未用 AI 改寫。
資料單位為每 100 g；TFDA 反式脂肪由原始 mg 換算為 g。未知值保留 `null`，缺核心營養素的紀錄不作照片自動營養配對。
每筆 USDA 資料有 FDC ID、原文名稱與官方查詢網址；TFDA 保留整合編號、俗名及內容物描述。
下載來源、匯入筆數、授權說明及 SHA-256 記錄於 `backend/nutrition_db_tw.source.json`、`backend/nutrition_db_usda.source.json`。
兩份 JSON 隨專案提供，啟動時不連外下載，也不需要 USDA API key。

## 實際發現與修改

- 提示詞改為逐容器、逐格檢查，主菜、主食與小份配菜分開列出；不重複計算整道菜及其食材。
- 要求只辨識可見證據，不猜隱藏餡料、蛋糕口味或看不清楚的背景小菜；估重須扣除骨頭與容器。
- 自動配對不再直接採用模糊搜尋第一筆，也不信任模型提供的任意替代食品。手動搜尋仍可提供建議。
- 對熟食拒用乾麵、濃縮湯與不相符的生肉資料；自訂食品每份數值須先正確轉成每 100 g。
- 前端保留照片辨識名稱，資料庫參考名稱另存，不再把辨識出的雞腿顯示成錯配的資料庫食品。
- 已辨識但缺營養資料的食品，在相簿、拍照及手動搜尋的結果區都可見；部分合計有明確提示。
- 照片結果缺少糖、纖維、飽和脂肪或反式脂肪資料時顯示「未提供」，並提醒相關合計可能低估；掃描結果的糖欄改為資料庫實際提供的「總糖」。
- API 為相容既有數字欄位仍提供數值換算結果，另附 `missing_nutrition_fields`、來源與提醒；不可忽略缺值旗標將占位 0 當成測量值。既有飲食紀錄會攜帶缺值提醒，歷史合計並未改成可空值的全新資料模型。

便當一的原圖可見兩份不同區域葉菜及混合豆干與豆類；小圖曾像紅蘿蔔的橘褐色塊，全尺寸較符合豆干，沒有把它當成已確認紅蘿蔔。

## 實驗與證據檔案

- `baseline.json`：修改前 13 張照片的真實模型輸出及當時營養結果，13/13 呼叫成功。
- `improved.json`：修正提示詞後，同 13 張照片重新呼叫模型，保留原始結果；其中營養結果是當時版本，不是最終版本。
- `database-only-replay.json`：固定修改前模型輸出，只更換最終資料庫與配對規則，協助分離資料配對和模型變動。
- `final.json`：將 `improved.json` 的原始輸出套入最終程式；屬離線重播，沒有再次呼叫模型。記錄兩份資料庫檔案雜湊以追溯版本；計算時統一換行為 LF，避免 Windows／GitHub 的換行轉換造成差異。
- `coverage-audit.json`：兩個便當與滷肉飯的額外二次檢查實驗。沒有多找到可確認的食品，兩次模型呼叫合計約 30–44 秒，因此沒有啟用到正式流程。

實際模型呼叫沒有傳入檔名、預期品名或測試答案。修正提示詞後的模型輸出仍可能隨再次執行改變。
正式照片辨識維持一次模型呼叫，營養查詢在後端本機完成。

### 重現離線檢查（PowerShell）

在專案根目錄執行：

```powershell
$env:NUTRILENS_SKIP_LOCAL_ENV='1'
$env:PYTHONIOENCODING='utf-8'
Push-Location backend
python -m unittest discover -s tests
Pop-Location
python tools/evaluate_food_images.py --replay docs/food-image-evaluation/improved.json --output docs/food-image-evaluation/final.json
npm --prefix frontend run typecheck
npm --prefix frontend run lint
npm --prefix frontend run test:scanner
npm --prefix frontend run test:records
npm --prefix frontend run build:web -- --clear
```

要重新呼叫中轉站測圖時，先移除測試用 `NUTRILENS_SKIP_LOCAL_ENV`，再執行下列指令；會讀取私有 `key.txt` 並產生 API 用量：

```powershell
Remove-Item Env:NUTRILENS_SKIP_LOCAL_ENV -ErrorAction SilentlyContinue
python tools/evaluate_food_images.py --output docs/food-image-evaluation/new-live-run.json --workers 3
```

沒有必要為營養配對規則的修改重複付費呼叫模型，可使用 `--replay`。

## 交接與下一步

營養資料及程式可隨公開儲存庫交付，官方原始大型 ZIP 與本地工作計畫留在忽略的 `.planning/`。
金鑰設定沿用原來的流程：私下交付**目前完整的專案根目錄 `key.txt`**，包含 Base URL、模型 ID 及全部金鑰，放到同學下載的根目錄即可。
不需要建立新的營養資料庫金鑰檔，也不是把金鑰貼到前端程式；完整步驟見根目錄 README。

要進一步量測成效，需要由人標註可見菜色、確認實際食材及份量，另收集未參與修改的測試照片，分開評估漏辨識、錯辨識、配對正確率和重量誤差。
提高營養估計可信度的有效補充是秤重、店家配方或實際包裝標示；資料庫擴充無法還原照片中看不到的內餡、油鹽與湯品配方。
