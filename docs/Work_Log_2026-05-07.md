## 遇到的問題與根因

### 1. Render `DATABASE_URL` 格式錯誤

問題：Render env value 曾誤填成 `DATABASE_URL=postgresql://...`，導致 psycopg 將 `DATABASE_URL` 當作 connection option，出現 invalid dsn。

根因：Dashboard value 欄位只應填值，不應包含 `KEY=` 前綴。

正確做法：

- Render key 填 `DATABASE_URL`。
- Render value 直接以 `postgresql://` 開頭。

### 2. Render CLI 不支援 env var 更新

問題：Render CLI v2.16.0 可查服務、deploy、logs，但沒有可用的 env var update 子命令。

根因：現有 CLI 功能範圍不足，env var 更新主要走 Dashboard、Blueprint 初始設定、MCP/API。

正確做法：

- 若要自動化 env var 更新，優先使用 Render API/MCP，並避免在聊天或 repo 中保存 API key。
- 若用 Dashboard，人工操作比瀏覽器工具自動化更可靠。

### 3. Dashboard env 表格不適合高風險自動化

問題：嘗試用瀏覽器工具自動化新增 env 時，表格會產生空白列與自動 generated value，造成 validation error。

根因：Dashboard 的 env 表格是動態 UI，button/input index 不穩定，且刪除按鈕缺少明確文字或 aria label。

正確做法：

- 不用不穩定 UI 自動化修改 secrets 或 env vars。
- 如果 UI 操作出現空白列或不可辨識刪除按鈕，立即取消/重新載入，不要硬存。
- 高風險設定改用 API、MCP，或由人手動確認。

### 4. Expo Web SSR 初始化 Supabase storage 錯誤

問題：設定 Supabase env 後，Expo Web SSR 報 `ReferenceError: window is not defined`。

根因：Supabase client 初始化時使用 React Native AsyncStorage；Web server render 階段沒有 `window`。

正確做法：

- Web 平台使用 guarded `window.localStorage`。
- Native 平台繼續使用 `@react-native-async-storage/async-storage`。
- 所有 browser-only API 都必須檢查 `typeof window !== 'undefined'`。

### 5. Supabase Auth user id 與 demo profile 不一致

問題：登入後 `user_id` 變成 Supabase Auth uuid，但後端沒有對應 profile，`GET /user/<uuid>` 回 404。

根因：先前 demo 流程固定使用 `demo_user`，正式 Auth 後沒有 migration 或首次 profile provisioning。

正確做法：

- Auth 登入成功後以 token subject 作為唯一 `user_id`。
- 若後端 profile 不存在，前端自動建立預設 profile。
- 不在正式 user-scoped API 繼續依賴 `demo_user`。

### 6. Supabase email rate limit 影響測試註冊

問題：測試註冊時遇到 `email rate limit exceeded`。

根因：Supabase Auth email provider/rate limit 限制，不適合大量或重複測試註冊。

正確做法：

- 使用既有測試帳號做登入驗收。
- 若要測註冊流程，先調整 Auth 設定或準備可收信測試帳號。

### 7. 聊天中貼出的 key 一律視為 compromised

問題：Supabase database password、Gemini keys、Render API key 曾被貼到聊天中。

根因：即使 assistant 不寫入檔案，聊天內容本身仍是外洩面。

正確做法：

- 不要在聊天中貼 secret；需要自動化時用本機 ignored env 檔、secret manager、MCP OAuth、Render Dashboard 或短效 API token。
- 已貼出的 key/password/token 必須輪替或撤銷。
- public publishable key 可以放前端 env，但仍避免不必要地重複散佈。

## 固定驗收流程

### 部署後基本檢查

1. 查 Render deploy 狀態，確認 latest deploy 是 `live`。
2. `GET /health` 應回 `200`，且 `status: ok`、`postgres: true`。
3. 用 Supabase 測試帳號取得 access token，不輸出 token。
4. 測 user-scoped API：
   - 無 token：應回 `401`。
   - 正確 token + 自己的 `user_id`：應回 `200`。
   - 正確 token + 其他 `user_id`：應回 `403`。
5. 啟動前端 Web，確認登入後首頁可同步後端紀錄。

### 修改 env vars 前檢查

1. 不在 git tracked 檔案放 secret。
2. 若使用 Render Dashboard，人工確認 key/value 列數與內容。
3. 若使用 API，API key 僅放於當次 shell session 或本機 ignored env，不寫入 repo。
4. env 修改後必須觸發 deploy/restart，並以 runtime 行為驗證，不只看 Dashboard。
