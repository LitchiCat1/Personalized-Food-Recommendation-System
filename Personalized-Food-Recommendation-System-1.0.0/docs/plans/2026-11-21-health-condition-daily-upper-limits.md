# 慢性病每日營養上限自訂

2026-11-21 · `v1.0.4` · 本機實作與隔離驗收完成。基準提交 `cb6bf4d`。Windows 伺服器部署結果另見下方紀錄。

## 1. 使用流程

1. 使用者在「個人檔案 → 健康狀況管理」勾選慢性病。系統沿用該病況目前的每日上限，並顯示可調整項目、預設值及單位。沒有每日上限項目的疾病只顯示既有健康資訊。
2. 展開已勾選的疾病後，每項提供「減少」按鈕、數字輸入欄、「增加」按鈕和「恢復預設」。以 g 計的欄位每次增減 1 g，鈉每次增減 1 mg；直接輸入仍支援原本精度。長按連續調整，放開即停止。調整先保留在表單，按「儲存」才生效。
3. 儲存後顯示該病況的設定值、來源（系統預設或自行設定），以及多病共存時首頁實際採用的上限。錯誤時保留輸入供修正，首頁仍使用最後一次確認的上限。
4. 「恢復預設」並儲存才清除該項自訂值，依當時的身體資料、熱量基準和病況公式重新計算。取消勾選只暫停套用，保留已儲存的自訂值；再次勾選時重新套用。舊版已清除的數值不會復原。

## 2. 採用規則

- 後端列出各已勾選病況可自訂的每日上限及其預設值。按照現有每日目標計算，逐條標明實際適用的營養素與規則。疾病有介紹文字或單餐門檻，不能直接當成每日上限。
- 各疾病每個營養素可獨立設定。自訂值可高於或低於該疾病的預設值，直接替代同一疾病的該項候選值。有其他疾病同時約束該項時，依現有優先規則決定適用項，再取適用候選中的較低上限。若仍受另一疾病限制，在頁面顯示實際限制來源。
- 對於目前依 `if/elif` 決定的脂肪與飽和脂肪規則，先保留既有分支優先序，只讓實際適用的候選參與。不得把每種疾病獨立算完後直接對整份目標取最小值，否則無自訂時也會改變多病組合的結果。
- 所有營養素都無自訂值時，現行輸出數值、目標類型和狀態完全相同。只調整有自訂且符合條件的營養素。熱量基準沿用既有設定流程。膳食纖維與其他 `minimum_target` 維持最低目標。蛋白質只有既有規則判為 `upper_limit` 時才可編輯。未歸屬特定疾病的全域上限維持既有行為。
- 每日自訂值影響首頁與共用目標的每日進度。歷史頁以現有讀取規則呈現目標，已記錄的餐點數值維持原樣。逐一驗證掃描器的每日鈉預算與推薦的剩餘每日預算是否讀取同一目標。單餐門檻、掃描的單餐風險、過敏原及病況專用排序規則沿用現有計算。
- 無論因取消勾選或多病並存而暫未套用，都保留已存的自訂值。多病規則優先序導致個別項目暫未生效時，標明該狀態。
- 繼續顯示目前的醫療提醒。自訂值標為個人設定。技術上的數值範圍僅用於輸入驗證，產品介面不把它標為建議攝取量。

## 3. 資料與相容性

| 區域 | 規劃 |
| --- | --- |
| 設定儲存 | 提議在 `users.doc` 增加 `daily_nutrient_limit_overrides`，結構為 `{condition_id: {nutrient_id: value}}`。沿用已驗證使用者 ID 與 SQLite 個人檔案。空白帳號與舊紀錄視為空對照表。 |
| 讀寫合約 | `GET /user/<user_id>` 回傳所有已儲存設定（含未勾選病況），僅提供已勾選病況的編輯資料。`POST /user` 省略欄位時保留原設定，送 `{}` 表示全部清除。每日目標只取目前勾選的病況計算。 |
| 寫入規一 | 以後端疾病 ID、營養素 ID 白名單和現行目標方向驗證。數值需有限、單位正確、符合精度與技術範圍。空白輸入提示修正，使用「恢復預設」清除。以同一份規格控制輸入與按鈕步進。 |
| 數值比較 | 以規一後的精度處理小數與比較。驗證剛好等於上限、剛高於上限，以及 `0` 是否可用。零值只在規格允許的欄位生效，進度禁止除以零，並測試首頁與後端狀態一致。 |
| 儲存與刷新 | 將個人檔案寫入序列化，表單送出期間停用同區重複寫入。後端以同一次更新保護保留與清除操作。分開處理「寫入失敗」與「寫入成功、刷新失敗」，避免已存的資料被舊畫面覆蓋。帳號切換或較舊回應不得覆蓋新帳號或較新結果。 |

## 4. 已核對的接點

- `frontend/app/(tabs)/profile.tsx` 目前有疾病核取控制、整份檔案同步和目標刷新，在此新增編輯入口。疾病勾選、過敏原、基本資料等其餘寫入路徑也要檢查相容性。
- `backend/app.py` 中的 `GET /user/<user_id>`、`POST /user` 搭配 `backend/services/profile_service.py` 管理檔案，`backend/repositories/storage.py` 將個人檔案存為 JSON。
- `backend/services/nutrition_progress_service.py` 計算每日值、方向及進度。`GET /records/<user_id>` 供首頁使用。同步檢查共用每日進度的洞察，避免進度百分比、超量狀態和目標值各自採用不同精度。
- `backend/services/medical_risk_service.py` 計算單餐上限及風險。驗收時比對設定前後輸出。

## 5. 實作順序與完成條件

1. **先鎖定現有行為。** 以目前五個病況的全部 32 種勾選組合建立預設目標回歸，再用不同熱量及體重案例驗證動態門檻。列出可自訂病況與營養素矩陣，逐項對照現行公式，確定單位、步進和技術範圍。
2. **接上 SQLite 與後端。** 個人檔案可新增、修改、清除與重開後讀回。測試舊資料、舊客戶端省略欄位、輸入非法值、取消勾選、越權讀寫和快速連續更新。覆蓋單病加減、同營養素多病取較嚴值、全部恢復預設。確認無自訂時的數值與方向相同。
3. **接上個人檔案與首頁。** 測試輸入、左右按鈕、單項重設、顯示多病的生效值，並驗證切到首頁立即看到最新上限及超量狀態。測試儲存失敗、刷新失敗及換帳號後的回應隔離。
4. **完成驗收。** 執行後端相關回歸及前端型別、lint、Web 匯出。在 Android 或窄版 Web 和桌面 Web 檢查觸控、鍵盤與版面。以隔離 SQLite 帳號跑完「勾選 → 預設 → 調低 → 調高 → 重啟 → 恢復預設」及雙病況案例，核對首頁、單餐風險與原飲食紀錄。將結果更新到本企劃書後結案。

## 8. 手機驗收後修正

- 以 g 計的欄位單擊增減 1 g，直接輸入仍支援一位小數；鈉維持 1 mg。兩個方向均可長按連續跳值，放開、中斷、關閉編輯器或離開畫面時停止。調整仍須儲存才生效。
